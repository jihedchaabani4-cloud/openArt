Status: DONE

## 1. Scope
Audit the persistence layer, storage keys, and generation execution states of the Prompt Bar. Investigate the data shapes of media values in `parameterValues`, `elements`, and `characters`, trace whether temporary or invalid URL protocols (`blob:`, `data:`) enter persistent storage, review all call sites and lifecycle behavior of `setIsGenerating`, evaluate the claim that Generate can become stuck after navigating away mid-flight, analyze prop vs store precedence for generation state, and inspect registry memory cleanup.

- Trace of async promise lifecycle across unmount and navigation.

## 4. Answers to Questions

### Q1: Media value shapes and blob URL persistence
- **Shapes in `parameterValues`**:
  - Library / gallery asset: `{ workflow_id, id, asset_id, url, preview, displayName, type, image_count, role }`.
  - Directly uploaded file: `{ name: file.name, url: "blob:http...", preview: "blob:http...", type: "image"|"video" }` created via `URL.createObjectURL(file)` in `MediaInput.jsx:51,70`.
  - Media list (`images`, `reference_images`): Array of the above objects.
  - Plain string: Workflow ID (e.g. `"wf_123"`).
- **Shapes in `elements` / `characters`**:
  - Normalized entity objects: `{ id, workflow_id, name, displayName, type, preview, url, image_count }`.
- **Can a `blob:` or `data:` URL reach the store and storage?**
  - **YES** (VERIFIED). `MediaInput.jsx` assigns `URL.createObjectURL(file)` directly into `parameterValues`. When `saveState` runs on subscription change, the `blob:` URL string is serialized to `sessionStorage`. On page refresh, the document-scoped blob URL is dead and fails to render.

### Q2: Call sites of `setIsGenerating` and stuck generation claim
- **Call sites of `setIsGenerating`**:
  - `src/features/prompt-bar/platform/PromptBarPlatform.jsx:150,392,399`:
    - Line 392: `setIsGenerating(true)` before awaiting `onGenerate`.
    - Line 399: `setIsGenerating(false)` inside `finally`.
  - `src/features/prompt-bar/store/createPromptBarStore.js:229`: store action definition.
  - `src/features/prompt-bar/__tests__/safe3Store.test.js:246,251`: characterization tests.
  - `src/features/prompt-bar/__tests__/safe4Persistence.test.jsx:191`: characterization tests.
- **Is the reset in a `finally`?**
  - YES. `PromptBarPlatform.jsx:399` has `finally { setIsGenerating(false); }`.
- **Does `finally` run if user navigates away mid-request?**
  - In standard JavaScript, an unmounted component does not abort promises unless explicitly aborted. The background async operation continues, and upon resolution or rejection, the `finally` block executes and mutates the store instance in `persistentStoreRegistry`.
- **Verdict on "Generate stays blocked after navigating back": PARTIAL** (VERIFIED).
  - Conditions under which it happens:
    1. If the network request hangs indefinitely without error/timeout (e.g. server socket hangup or infinite streaming).
    2. If an unhandled exception occurs inside `serializeAndEmit()` before entering the `try` block.
    3. If the user navigates away to another page within the same project while generation is pending: when mounting on the new page, the shared in-memory store has `isGenerating === true`, which disables the Generate button until the background request completes.
    4. If a tab crash or navigation halts execution before `finally` runs, the in-memory store retains `isGenerating: true`. (However, full page reload clears memory and starts with defaults since `isGenerating` is not persisted to sessionStorage).

### Q3: Parent prop vs store `isGenerating`
- `PromptBarPlatform.jsx:142` resolves:
  `const isGenerating = Boolean(propIsGenerating || storeIsGenerating);`
- Neither overrides the other: it is a logical OR.
- If the parent passes `isGenerating={isGeneratingMutation}` and the React Query mutation is pending, `isGenerating` is `true`.
- If the store has `storeIsGenerating === true`, `isGenerating` is `true`.
- The button is disabled (`isGenerateDisabled`) if either is `true`.

### Q4: Storage keys and registry lifecycle
- **SessionStorage keys created during normal use**:
  1. `studio-prompt-bar_<projectId>` (or `studio-prompt-bar_global` on non-project routes).
  2. `cinema_studio_entry_<projectId>` (created by studio layout).
  3. `openart_pending_prompt_action` (transient, removed once consumed).
- **Does anything ever call `clearPersistentPromptBarStores`?**
  - **NO** (VERIFIED). `clearPersistentPromptBarStores` is called ONLY in test files.
  - In production, `persistentStoreRegistry` accumulates every project store instance in memory indefinitely across the tab's lifespan.

## 5. Verdict
**CONFIRMED (Storage leak & memory leak) / PARTIAL (Stuck button)**:
- `blob:` URLs leak into sessionStorage due to missing sanitization in `saveState`.
- `persistentStoreRegistry` is never cleared in production, causing unbounded in-memory store retention.
- Generate button blocking across navigation is conditional on in-flight or hanging requests.

## 6. Risks
- Memory leak in `persistentStoreRegistry` as users navigate between multiple projects in the same session.
- Stored `blob:` URLs break visual slot previews after tab refresh.

## 7. What Could Not Be Verified
- Real-world browser crash logs caused by memory exhaustion from accumulated stores.
