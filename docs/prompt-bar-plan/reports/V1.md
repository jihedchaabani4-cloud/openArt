# V1: Instances, Mounting, and Project Identity Verification Audit
Status: DONE
Task: V1
Phase: P1

## 1. Scope
Investigate where and how `PromptBarPlatform` is mounted across the entire application, whether multiple instances can exist concurrently, how project identity is resolved during server vs client execution, caller expectations of the singleton `activePromptBarStoreInstance`, and verify the claim of server/client hydration mismatch.

## 2. Method
- Code search via `git grep -n "PromptBarPlatform" src/` and `git grep -n "from.*prompt-bar" src/`.
- Inspection of all mounting sites: `src/app/cinema-studio/[projectId]/assets/page.js`, `src/app/cinema-studio/[projectId]/collection/[collectionId]/page.js`, `src/widgets/StudioLayout/NewProjectView/NewProjectView.jsx`, and `src/app/cinema-studio/test/prompt-bar-compare/page.jsx`.
- Inspection of `PromptBarStoreContext.js` (`resolveProjectId`, `loadSavedState`, `saveState`, `PromptBarStoreProvider`).
- Search for dynamic SSR opt-outs (`git grep "next/dynamic" src/`).
- Analysis of Next.js `"use client"` boundaries and `next.config.mjs`.
- Trace of all call sites of `getActivePromptBarStore` and `setActivePromptBarStore`.

## 4. Answers to Questions

### Q1: Where is a Prompt Bar mounted today?
`PromptBarPlatform` is rendered in exactly 4 files:
1. `src/app/cinema-studio/[projectId]/assets/page.js:362-368`
   - Props: `type={generatedMediaType}`, `featureConfig={generatedMediaConfig}`, `models={realModels}`, `onGenerate={handleGenerate}`, `isGenerating={isGeneratingMutation}`.
   - Defaults: `persistKey` defaults to `"studio-prompt-bar"`, `projectId` not accepted.
2. `src/app/cinema-studio/[projectId]/collection/[collectionId]/page.js:472-478`
   - Props: `type={generatedMediaType}`, `featureConfig={generatedMediaConfig}`, `models={realModels}`, `onGenerate={handleGenerate}`, `isGenerating={isGeneratingMutation}`.
   - Defaults: `persistKey` defaults to `"studio-prompt-bar"`, `projectId` not accepted.
3. `src/widgets/StudioLayout/NewProjectView/NewProjectView.jsx:60-65`
   - Props: `type={generatedMediaType}`, `featureConfig={generatedMediaConfig}`, `models={models}`, `onGenerate={() => {}}`.
   - Defaults: `persistKey` defaults to `"studio-prompt-bar"`, `isGenerating` defaults to `false`.
4. `src/app/cinema-studio/test/prompt-bar-compare/page.jsx:54-63`
   - Props: `type={generatedMediaType}`, `featureConfig={generatedMediaConfig}`, `models={models}`, `onGenerate={...}`, `hideBackground={true}`.

### Q2: Can two bars be mounted at the SAME time?
- **In production**: NO. In production, `assets/page.js`, `collection/.../page.js`, and `new/page.js` are mutually exclusive route pages. Modals (e.g. `NewElementDialog`, `CreateElementModal`, `ConfirmDeleteDialog`) and character/element detail pages do NOT mount `PromptBarPlatform`.
- **In test pages**: YES. `src/app/cinema-studio/test/prompt-bar-compare/page.jsx:139-152` mounts `Instance A` and `Instance B` concurrently side-by-side in the "Instance Isolation" tab.
- **Architectural implication**: Because `PromptBarStoreProvider` uses a module-level `activePromptBarStoreInstance` singleton, mounting two bars simultaneously breaks external callers (`addMediaToPrompt`, `animateMedia`, `useMediaActions`) as they will bind to whichever provider rendered last. `instanceId` is therefore necessary to support side-by-side instances and future modal/drawer integrations without collision.

### Q3: How does `resolveProjectId()` get the project id?
- It inspects `window.location.pathname` using regex `/\/cinema-studio\/([^/]+)/` (`PromptBarStoreContext.js:37-43`).
- It does NOT use route params, React Context, or store state.
- **Is it available during SSR?** NO. `typeof window === "undefined"` on the server, so `resolveProjectId()` returns `null`.

### Q4: Are the pages client components only? Is the bar rendered during SSR?
- All mounting pages have `"use client"`.
- Under Next.js App Router, `"use client"` components ARE pre-rendered on the server into HTML during initial request; `"use client"` only marks the hydration boundary.
- `next/dynamic` with `{ ssr: false }` is NOT used anywhere in the codebase.
- Therefore, `PromptBarPlatform` and `PromptBarStoreProvider` execute during SSR on the server.
- `reactStrictMode` is default enabled (`true`).

### Q5: Callers of `getActivePromptBarStore` and `setActivePromptBarStore`
1. `src/features/prompt-bar/store/PromptBarStoreContext.js:18,21`:
   - `setActivePromptBarStore`: writes `activePromptBarStoreInstance = store`.
   - `getActivePromptBarStore`: returns `activePromptBarStoreInstance`.
2. `src/features/prompt-bar/store/PromptBarStoreContext.js:142,147`:
   - Calls `setActivePromptBarStore(storeRef.current)` during render body (line 142) and inside `useEffect` (line 147).
3. `src/features/studio/core/mediaReferenceService.js:221,390`:
   - `addMediaToPrompt`: expects `store.getState()` to provide `activeMode`, `selectedModelId`, `modelsMap`, `parameterValues`, and `setParameter`.
   - `animateMedia`: expects `store.getState()` to provide `setActiveMode("video")`, `setActiveSubMode("frames")`, and `setParameter("input_image", ...)`.
4. `src/features/workflows/model/useMediaActions.js:150`:
   - Reads `activeBarStore = getActivePromptBarStore()` to set mode, subMode, and `input_image` during "Animate" user actions from asset cards.

### Q6: Claim to settle: Hydration mismatch between server and client keys
- **Verdict: CONFIRMED** (VERIFIED).
- **Evidence**:
  1. On the server during SSR, `typeof window === "undefined"`. `resolveProjectId()` returns `null`. The computed key is `${persistKey}_global`. `loadSavedState` returns `null`. The server renders HTML using default values (`prompt: ""`, default model).
  2. On the client during initial hydration on route `/cinema-studio/proj_123/assets`, `window` is defined, `resolveProjectId()` returns `"proj_123"`. The computed key is `${persistKey}_proj_123`.
  3. `PromptBarStoreProvider` (lines 113-125) reads `loadSavedState("studio-prompt-bar_proj_123")` synchronously inside the component render body to initialize `storeRef.current`.
  4. If sessionStorage has saved state for `proj_123` (e.g. non-empty prompt or different model), the initial client render tree differs from the server-rendered HTML markup, triggering a React hydration mismatch error.
  5. This confirms the necessity of Decision PB-D-06 (store creation is deterministic from default type props; saved state is applied only after mount inside a client-side `useEffect`).

## 5. Verdict
**CONFIRMED**: The server/client key divergence and synchronous hydration read during render causes hydration mismatch when stored state exists.

## 6. Risks
- Hydration mismatches can cause React 19 to discard server HTML and re-render the entire tree, causing UI flicker and dropping focus.
- The render-phase mutation of `activePromptBarStoreInstance` (line 142) violates React concurrent rendering and StrictMode rules (double invocation leads to unpredictable active store references).

## 7. What Could Not Be Verified
- Real production traffic error telemetry for hydration warnings, as this audit is conducted in a local hermetic environment without live telemetry feeds.
