### Q2: Consumption and state of `characterType`
- **Who consumes `characterType` today?**
  - ZERO screens or components mount `PromptBarPlatform` with `characterType`.
  - It is imported ONLY in the test file `src/features/prompt-bar/__tests__/safe2TemplateRules.test.js:19`.
- **What is missing for a real Character Prompt Bar?**
  1. `character.type.js` declares `referenceSlots: []` and `layout.showAttachmentBar: false` (no slots exist).
  2. It has no `featureConfig` (no `resolveParameterMapping`, no `COMPOSITION_REQUIREMENTS`, no `filterEligibleModels`).
  3. No screen mounts it (`characters/new/page.js` uses an archetype cards grid, not a prompt bar).
  4. It lacks integration with character traits and persona form fields (`useCharacterStore.features`).
  - **Plan impact**: Validates PB-D-18 (Character template is LOCKED until P8; generated-media is the only real template).

### Q3: Spec 033 Intention vs Reality (5 lines)
1. **Intended**: Core is strictly feature-agnostic with zero knowledge of modes, frames, or roles. **Reality**: `createPromptBarStore` hardcodes `activeMode: "image"`, `activeSubMode: "frames"`, `elements`, and `characters`.
2. **Intended**: Platform has zero feature-specific branching. **Reality**: `PromptBarPlatform.jsx` is 1100+ lines with 15+ hardcoded branches on `"video"`, `"frames"`, and swap buttons.
3. **Intended**: In-memory only with no persistence across mounts. **Reality**: `persistentStoreRegistry` caches stores in memory across route changes and writes 7 fields to `sessionStorage`.
4. **Intended**: Reusable across multiple templates (Character, Image Edit, Video Edit). **Reality**: Only `generatedMedia` is implemented; `characterType` is an unused 20-line stub.
5. **Intended**: Isolated slots preventing key collisions across modes. **Reality**: All media is stored flat in `parameterValues`, causing PB-K1 collisions between `input_image` as reference vs start frame.
